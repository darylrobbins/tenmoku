# Add Open Keyboard Shortcuts: a tab, as VS Code's Keyboard Shortcuts editor, listing each command with its keybinding, when and source, searchable by command or keystroke, with conflicts marked and Remove / Reset Keybinding on a row (Mac T1100)

## Problem
No UI lists what is bound to what. VS Code's Keyboard Shortcuts editor (cmd-K cmd-S) is a table of Command / Keybinding / When / Source with search, conflict warnings and a context menu. Cards 5 and 6 give the model and the file writes; this card is the tab, commands and removal. Recording a new keystroke is card 8.

## Change
- New `crates/fe-workbench/src/shortcuts_editor.rs`, a pane item built like card 3's `SettingsEditor` (if that card has not landed, follow `DiffView`/`FileViewer`; the two items share no code and may merge in any order; if both exist, extract nothing, duplicate the small open-or-focus helper).
- The keymap and catalog are what the workbench already holds for menus and the command palette (`command_catalog.rs`, `KeymapStore`); read them, do not rebuild from the registry a second time. Hot reload: subscribe to the same keymap-reloaded event the menu bar uses.
- Commands via `#[kiln::command]` in `workbench_commands.rs`; defaults in `crates/fe-keymap/keymaps/fastedit.toml` (check `secondary-k secondary-s` is still unbound with rg before choosing it); menu entries in `menus/fastedit.toml`; tables in `typed_command_ids_tests.rs` and `command_catalog_tests.rs` get rows. `tests/menu.rs` has menu-wide invariants (every item's command is registered); keep it green.

## Tests
New `shortcuts_editor_tests.rs` and `crates/fe-keymap/tests/keyboard_shortcuts_binding.rs` (modelled on `search_toggle_details_binding.rs`). Linux-OK. Expect textual conflicts with other cards appending to fastedit.toml, workbench_commands.rs and the command tables.

## Implementation notes

- **Keymap reload.** The menu bar has no reload event to subscribe to: `kiln_platform::keys::set_keymap` swaps the matcher's keymap, reinstalls the menus and redraws every window, and the in-window menu bar reads `current_keymap` as it draws. The tab does the same: drawing, it compares `fe_gpui::current_keymap` with the `Arc` its rows came from and rebuilds the model if they differ. A tab in the background rebuilds when it's next shown. Edits don't install the keymap themselves; the config service's watcher reloads `keymap.toml` once `write_keymap` lands (checked by hand under Xvfb), and the tests reload it as the watcher would.
- **Commands.** The typed commands, the app registry's, and `command_list()`, which `init` now keeps in a `ListedCommands` global as well as giving it to the palette, so the registries aren't built again. Unlisted typed commands appear only when bound.
- **Source.** `ShortcutBinding::source` (card 5) says Default for layer 0 only, but the app's store lays fastedit's keymap over kiln's and its modules' layers, so in the app every binding read User. The tab takes a binding's source from its location instead: User if its entry is in the user's `keymap.toml`, else Default. That covers the Source column, Reset Keybinding's check and `@source:user|default` in the search, which the tab filters itself before the rest of the query goes to `ShortcutsModel::search`. The test harness lays an empty kiln layer under fastedit's, as the app does. The model's own `source` is card 5's to fix.
- **Conflicts** (review round 1, F2) are `Keymap::report_with` in the contexts the workbench has, as the keymap's own contexts tell them: `[workbench]`, `[workbench, editor]`, and for each distinct `when` a binding has, a stack where it holds, built from a term of it in disjunctive normal form (a vim key such as `vim.mode == normal` implies `vim.enabled`). So a `workbench` and a `terminal` binding of the same keys clash in `[workbench, terminal]`, while `project_panel` and `editor`, or `editor && vim.mode == normal` and `editor && !vim.enabled`, never share a context and don't. Pairing every two contexts instead flagged ~270 clashes in the default keymap, nearly all between panels that are never focused together; this gives 77, each a real one (vim's keys over the editor's, the terminal's over the workbench's), in about 6 ms. A shadowed chord prefix gets the warning too, its tooltip saying which longer keys it starts. A hidden binding's tooltip names the location of the entry that replaces it.
- **Default layers for edits** (F1). Remove and Reset read the user's file on every layer the app ships, not fastedit's alone: kiln-platform's config service now publishes the keymap store it reloads (`config::keymap_store(cx)`, with `SharedKeymap::defaults` and kiln-core's `KeymapStore::defaults`), and the tab passes `write_keymap_on` fastedit's `DEFAULT` as shipped and every other layer written back out as TOML as read on this platform. Without a store (no config service) it falls back to fastedit's alone. The tests run a real `ConfigService` over kiln's bundled keymap and fastedit's, reloaded by batches as the watcher sends them.
- **Reset eligibility** (F3) is a dry run: Reset is offered when `edit_keymap_on(ResetCommand)` would change the user's file as last read or written, so entries not in effect count too (another platform's, one a later entry unbinds, an unbind of a default in any layer). The tab reads the file off the main thread when it opens and when the keymap reloads.
- **Menu.** No context menu component exists; the tab draws kiln-ui's `MenuPanel` in a deferred, anchored element at the click, closed by Escape or a click outside. It lists only the items that apply to the line: Remove isn't offered on a hidden binding (removing its keys would take the winner too), Reset only on a command with a user binding or a user unbind entry of one of its defaults. The menu items "Keyboard Shortcuts" and "Keyboard Shortcuts (JSON)" follow Settings… in the app menu (macOS) and File (elsewhere).

- **Review round 2.** F4: any vim flag or key in a witness (`vim.visual`, `vim.pending`, `vim.mode == …`) now brings `vim.enabled`, so none clashes with an `!vim.enabled` binding. F2 (part): each witness with an editor's frame is also tried with every combination of the editor's own flags (`completion`, `ghost_text`, `proposal`, set on that frame as fe-gpui's `EditorView` sets them), which catches the shipped Down (`completion.select_next` over `editor.move_down`), ghost text's accept-word over the word motion, and conditions that are independent on one editor (`editor && completion` with `editor && vim.mode == insert`). F5: the tab observes `ChangedFiles` and re-reads the user's file when the watcher names it, even if the keymap in use is unchanged, and an open menu's items follow the read.
- **Review round 3.** F2: every alternative of a context gets its witness, not just the first that holds, so `settings_editor || shortcuts_editor` and `vim_line || shortcuts_editor` clash in the Keyboard Shortcuts tab (test `alternative_branches_clash`).

## Known limits

Narrowed by respec after review rounds 2, 4 and 6 (criteria C3 and C4); the follow-ups are T305, T306, T313 and T314.

- **Conflict marks are advisory and may miss vim-only clashes (C3, follow-up T305).** Conflicts are found by `Keymap::report_with` in witness contexts built from each binding's predicate atoms, with the editor's own flags (`completion`, `ghost_text`, `proposal`) combined onto every editor context and `vim.enabled` implied by any vim flag or key. Every viable alternative of a predicate gets its own witness (round 3's fix, test `alternative_branches_clash`), which is more than C3's limit allows for; what's left of T305 is the rest of vim's stamp (`VimState::stamp`: the visual flag only in visual mode, `vim.pending_kind` only while pending, the cmdline kind only on the command line), so a clash that only exists under such a combination may go unmarked. The mark never drives a write; a missed one costs only a missing warning.
- **Reset reads non-fastedit defaults as on this OS only (C4, follow-up T306).** kiln-platform's keymap store holds the default layers other than fastedit's (kiln's, its modules', extensions') only as read on this platform; fastedit's own layer is passed to edits as shipped, with every platform's keys, so its defaults reset as before. Reset deletes only the user entries it can attribute: those naming the command, and unbinds of a default of it the store knows; it never writes a change for one it can't. Three shapes follow; the last two are out of scope for C4, documented as its limit (review F6, accepted) and fixed by T306:
  - Refused, fail-closed: when a command's default comes from one of those layers and the user's file has an entry gated on another platform that names the command or unbinds keys, Reset Keybinding shows disabled with the hint "Edit keymap.toml", and choosing it writes nothing (test `reset_is_disabled_for_another_platforms_entry_on_a_kiln_default`).
  - Not handled: an ungated unbind whose keys mean a kiln or extension default only on another OS (a context-free `cmd-shift-p` unbind written on Linux turns kiln's palette key off on macOS) is left in place by Reset.
  - Not handled: a command whose kiln or extension default is filtered out on this OS (kiln's Linux-only F10 seen from macOS) isn't known to have that default, so another platform's unbind of it gets no refusal.

  Reset eligibility is re-read from `keymap.toml` on every `ChangedFiles` notification naming it.
- **Edit order and the refusal's freshness (C4 limits (e) and (f), review round 6; follow-ups T313 and T314).** (e) Each edit from the tab is its own background write, so two quick edits (Remove then Reset), or a write begun by a tab that is then closed, may land out of order; T313 adds an ordered write queue. (f) Reset's "Edit keymap.toml" refusal is checked on the tab's cached copy of `keymap.toml`, re-read on every `ChangedFiles` notification naming it, so a gated unbind saved between opening the menu and the click may slip past it; T314 re-checks on the text actually edited. Either way, a write that lands edits the file as read at write time (`write_keymap_on` reads, edits and renames into place, retrying once if the file changed) and never corrupts it.
