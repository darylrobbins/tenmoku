# Fix flaky fe-workbench plugin_events::plugin_events_tests::a_plugin_that_falls_behind_never_slows_typing: its 20 s wall-clock bound on 1000 keystrokes measures machine load, not the plugin

## Problem

`fe-workbench plugin_events::plugin_events_tests::a_plugin_that_falls_behind_never_slows_typing`
fails now and then under gate load. Seen in main's post-merge check on
6461e112 (run 01m6t8gwd64x0qx2wfdm98p5a0, test_all.fastedit-all.log
~6050). It was the only failure:

    panicked at crates/fe-workbench/src/plugin_events_tests.rs:576:
    typing took 20.491937194s

helium's loadavg was about 55-68 on 24 cores at the time: two batch gates
and several finishes were running.

## Cause

The test (crates/fe-workbench/src/plugin_events_tests.rs:550-599) sets
`limits.event_queue = 1`, loads a listener for OPENED | CHANGED, holds its
deliveries (`inbox.hold(true)`), fills the queue by opening `b.txt`, then
types 1000 chars with `cx.simulate_input` and asserts
`took < Duration::from_secs(20)` (line 576). In a debug build under heavy
load, the 1000 keystrokes alone take close to 20 s, with or without a
plugin. So the bound measures machine load, not the plugin.

The bound is also a weak proxy for the property. The held plugin's thread
spins in `Inbox::pop` (plugin_events.rs:114-120) and takes nothing, so if
`Inbox::push` (plugin_events.rs:97-111) ever waited on the plugin, typing
would hang for good. It would not run a bit slow.

This is not a production bug.

## Fix (test only)

Keep the test's intent, "a plugin that falls behind never slows typing",
and its other assertions: all 1000 chars applied, `inbox.len() == 1`
("bounded"), and then BufferOpened(a), Lagged(1), and one merged
BufferChanged at version 1001 with ranges 0..1000. Replace the absolute
20 s bound with a check that load can't break. In order of preference:

1. Assert what can be seen without a clock. While typing, the held plugin
   delivered nothing (`inbox.deliveries()` has the same length before and
   after `simulate_input`). The host still pushed a change for every
   keystroke (the existing `changes(&inbox)` helper at line 394 grew by
   1000, each one for `b_id`, the last at version 1001). The queue stayed
   at 1. So every keystroke was applied, and its
   event was pushed and merged, while the plugin took nothing. That is
   the property: typing never waited on it. Drop the `Instant` timing,
   or keep it only in the failure message.
2. If you keep a timing check, make it relative. Time the same typing
   with no plugin held, as a baseline in the same test (for example into
   a buffer before the listener loads, or into a.txt with the listener
   unsubscribed), and assert held <= baseline * 5 + 2 s, or similar
   generous slack. Both runs see the same load.
3. Last resort: fewer keystrokes (for example 200) and a much larger
   bound (60 s or more). If you take this route, the `version: 1001` and
   `one(0, 1000)` expectations change to match.

Change only crates/fe-workbench/src/plugin_events_tests.rs. Don't change
plugin_events.rs, plugin_host.rs or kiln-plugin's EventQueue. If you need
a new test-only accessor on `Inbox`, block and ask for a scope respec
first; the `pushed()` and `deliveries()` accessors already there should
be enough. Don't add a regression test: a test-only flake fix is proven
by repeated runs under load.

The test came over from the Mac (Mac T1347, helium T278). The Mac copy
probably has the same bound. That is out of scope here.
