# Open Editor at Index 1 to 9 and Last Editor in Group (ctrl-1 to ctrl-9 on macOS, alt-1 to alt-9 elsewhere), as VS Code's workbench.action.openEditorAtIndex1-9 and lastEditorInGroup

fastedit has next/previous tab but no way to jump to the Nth tab. VS Code: workbench.action.openEditorAtIndex1..9 (ctrl-1..9 on macOS, alt-1..9 on Windows/Linux), and workbench.action.lastEditorInGroup. Nothing to do when the tab does not exist.

Design: one typed command workbench.open_editor_at_index taking an index argument rather than nine ids (a divergence from VS Code's ids; note it in the module doc), bound nine times in fastedit.toml with args. If the typed-command macro or the catalog check (command_catalog_tests.rs "catalog.check(id, args)") cannot take args for a workbench command, fall back to nine ids generated by a small macro_rules in the module and say so. workbench.last_editor_in_group is a second command. New module tab_index_commands.rs with its own "#[kiln::command] impl Workbench" block (pattern: find_commands.rs); the active pane's tab list is Pane::tabs(); add one pub fn on Pane in pane.rs that activates a tab by index through the same path as Pane::cycle (cycle_items), so focus, preview and nav history behave the same as the Next Tab command.

Keys: check at drafting time ctrl-1..9 and alt-1..9 were unbound; secondary-1 and secondary-0 exist only in the ImageViewer context (cmd-1 there must keep working). On macOS ctrl-digit may reach the terminal panel when it has focus: bind in the workbench context and confirm a focused terminal still gets its keys (terminal context should win); add that to the key test.
